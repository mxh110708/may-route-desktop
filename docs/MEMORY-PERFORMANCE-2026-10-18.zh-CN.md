# 内存优先的性能优化与验收（2026-10-18）

主目标是驻留内存，次目标是 CPU，覆盖代理停止／运行和界面前台／后台四种组合。正常操作、代理传输、故障切换、日志、连接记录、编辑草稿及终端会话属于约束，不能以减少功能或中断会话换取数字。

## 本轮实现

1. 应用辅助进程完成配置校验、格式化、模式生成或配置编码/解码后，连续 10 秒没有应用 RPC 工作时，一次性调用 Go `debug.FreeOSMemory` 回收未使用的堆。新请求推迟定时器；活动应用流保护正在进行的工作。回收后不再定时执行，直到下一批配置工作完成。该机制仅接入 `runWorker`，代理服务进程没有新增回收策略，也没有降低 Go 并发、改变 `GOGC` 或设置额外堆内存上限。
2. 连接等本来会在下一次订阅时重建的流，在最后一个订阅者离开后立即释放旧表。多个订阅者共用时继续保留；普通日志缓存不使用此清理策略。连接页仍打开但窗口隐藏时，继续接收有界连接历史：核心的关闭连接缓存可能被 GC 清理，不能依赖重新订阅补回全部历史。该活动流也可能推迟停止后台的辅助进程释放，以保留记录为先。
3. 恢复日志滚动时释放暂停期间的冻结副本。暂停操作仍显示原快照，恢复后显示实时日志，日志数量上限不变。
4. 导入字体时使用原始字节视图，保留偏移和长度，减少额外整份复制。加载完成后才把最终选中的字体加入 `document.fonts`；快速切换产生的迟到字体及失败选择清理缓存。当前字体继续保留，恢复默认后释放自定义字体对象。
5. 保留上一轮的隐藏界面订阅暂停、停止后台辅助进程释放，以及终端/Markdown 首次使用加载。所有功能文件随安装包内置。没有通过关闭活动终端、丢弃草稿、重载页面、裁剪 Windows 工作集或替换字体/图标减少数字。

低内存限制和降低 Go 并发的实验结果存在波动，未采用这些参数。

## 辅助进程单独实测

同一签名 Electron 父进程、同一认证和命名管道，交替运行原版与新辅助进程各三次。每次完成五轮模式生成、2500 个合成出站的校验及格式化，等待 15 秒后采集三次。测试仅处理合成配置，不启动正式服务。

| 指标（中位数） | 原版 | 新实现 |
| --- | ---: | ---: |
| 辅助进程私有工作集（MiB） | 18.92 | 13.36 |
| 空闲后再次格式化（毫秒） | 1.25 | 1.71 |

这批配置处理后减少约 5.56 MiB（29%）驻留内存。再次调用差异小于 1 毫秒。该数字只针对辅助进程，不是整个 Route 的百分比；轻量配置和长期空闲的原版辅助进程可能本身已接近 8–10 MiB，不能重复计入同一收益。

## 四种状态的对比方法

使用独立签名的测试程序、真实界面组件、真实桌面 IPC 桥及辅助进程，连接一个独立的 `StartedService` 实例。基线界面来自本轮修改前的 dashboard Git HEAD，基线辅助进程为修改前的正式构建；优化模式使用当前源码。两者使用同一 Electron 版本、字体、尺寸和合成配置。

运行场景通过随机 loopback mixed 端口向独立本地 HTTP 服务器持续传输 64 KiB 数据，并逐次校验 SHA-256。只使用测试端口，不设置系统代理，不启用 TUN，不访问用户现有服务或真实节点。停止场景不启动该代理实例。

每格两轮，第二轮反转先后顺序；每次完成相同配置处理，等待 22 秒后取得三个私有工作集、提交内存和累计进程 CPU 样本。采样页面为概述；连接页、日志页和终端另作功能验收，不宣称每个页面都具有相同内存。只汇总测试自己的 Electron、辅助进程和独立代理进程，不计测量 PowerShell 的开销。前后台由文档可见性模拟，所有原生窗口始终隐藏，未操作鼠标；硬件加速统一关闭以使离屏测试一致。

下表为六个样本的私有工作集中位数。最后一列另列每轮末次样本的中位数，避免把启动阶段 V8 回收时点的不同全部当作持续收益。

| 状态 | 基线（MiB） | 优化（MiB） | 每轮末次样本：基线 → 优化（MiB） |
| --- | ---: | ---: | ---: |
| 停止，前台 | 131.89 | 119.93 | 129.40 → 112.73 |
| 停止，后台 | 122.91 | 102.83 | 119.27 → 98.20 |
| 运行，前台 | 155.94 | 145.92 | 154.21 → 144.58 |
| 运行，后台 | 166.09 | 136.85 | 144.13 → 135.05 |

运行后台的全部样本差值约 29 MiB，而末次样本差值约 9 MiB，说明整棵进程树的启动回收存在明显波动。因此不把 29 MiB 当作长期保证，也不从本表直接推断安装实例的固定内存。

| 状态 | 基线区间 CPU | 优化区间 CPU |
| --- | ---: | ---: |
| 停止，前台 | 0.80% | 0.56% |
| 停止，后台 | 1.20% | 0.72% |
| 运行，前台 | 2.87% | 2.79% |
| 运行，后台 | 4.14% | 1.52% |

这里 CPU 以一个逻辑核心为 100%，包含独立 HTTP 数据发生器，来自每轮首末样本之间累计 CPU 的差值，再取两轮中位数；本机有 24 个逻辑处理器，任务管理器的全机比例约为这些数字的 1/24。运行前台的微小差值不作显著改善结论。本轮未观察到持续 CPU 增加。

8 次运行场景累计通过真实代理传输并校验 109,051,904 字节，没有失败。停止后台按需重建辅助进程并完成格式化约 601 毫秒；其他场景的该次调用约 4–10 毫秒。主界面和草稿无需重载，但停止后台后首次使用辅助进程的操作存在这段冷启动等待，不能称为绝对零延迟。

与任务管理器中的正式安装实例仍有边界：测试不加载真实用户配置，不包含完整正式托盘/系统服务管理，测试代理使用 loopback RPC 而非正式特权服务 relay。因此结果用于比较相同测试条件下的前后差异，不是 Clash 对比或真实网络吞吐跑分。

## 正常使用验收

最终本地构建通过 147 项桌面 Node 测试、86 项界面测试和 4 项 Go 内存生命周期测试；TypeScript、界面 lint、样式及安装数据恢复检查通过。签名安装包在本机构建，隔离验收没有替换现用客户端。正式发布对应的源码提交记录见发布说明。

自动化检查和隐藏真实界面验收覆盖：流的暂停/恢复、迟到帧丢弃、共享订阅和缓存清理；字体字节范围、迟到加载、真实 Chromium 字体解码；日志暂停/恢复；编辑草稿保留；终端输入输出及隐藏/主题切换后保留同一会话；版本说明表格、表情、外链和转义；后台辅助进程按需恢复及活动工作保护。

额外的真实核心测试最初发现：关闭连接缓存会随核心 GC 清理，且原界面的可见性事件会强制重新订阅。已增加连接历史专用保护：保持打开的连接页在后台继续接收事件；恢复可见时保留健康的现有连接流，手动重连和网络恢复仍可强制重连。修正后验证后台前后的旧关闭记录与新增记录都在，离开页面后旧表释放，重新进入时重建当前活动连接；长连接保持到主动结束并完成内容校验。隐藏期间日志可补回，真实停止/启动、节点选择及后续传输也通过。该测试与四场景统计分开保存，未混入其内存结果。

CPU 不以瞬时任务管理器的 0% 推断。比较采样区间累计进程 CPU 的增量；一次配置处理和一次性堆回收另算，不承诺所有负载下 CPU 恒为 0。现有代理、自动故障切换、恢复监控和日志归档的职责没有改变。

原始数据和独立验证脚本保存在本地 `.codex-tmp` 验证目录，不随安装包分发。历史后台测量见 `BACKGROUND-PERFORMANCE-2026-10-18.zh-CN.md`；按需加载的独立测量见 `STARTUP-PERFORMANCE-2026-10-18.zh-CN.md`。不同测试不能直接相加，也不能把脚本字节减少比例当成内存减少比例。
