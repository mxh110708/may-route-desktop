# Windows 代理重复应用与 WSL 通知

## 原因

Windows 守护进程对 `StartedService`、`ManagedService` 的调用先进行拥有者授权，随后调用 `PrepareOwner`。旧实现即使已经持有同一用户、同一会话的令牌，也调用 `applySystemProxyLocked`。后者在代理偏好为开启时执行 `WindowsSystemProxy.Enable`，最终调用 WinINET 写入代理设置。

因此，读取状态或重新订阅也会产生代理写入。桌面端正常情况下约每分钟读取一次 `getClashModeStatus`，可以在未发生代理恢复、设置值也未变化时反复应用代理。这还会绕过桌面层对其他代理接管的避让逻辑。不能通过仅检查界面层的恢复日志排除这条路径。

2026-10-23 北京时间 17:23:32–17:25:40 的只读采样中，65 次代理开关、地址观测均相同，但 Internet Settings 键最后写入时间出现五个不同值。这与上述路径吻合；注册表键时间本身不能将每条 WSL 通知归因于具体进程。

本次只读核对安装版核心的嵌入版本为 `1.14.2-ab966ec7a`，与本次修复前核心源码修订一致。

## 修复边界

- 已有同一拥有者和会话时，`PrepareOwner` 直接返回，不应用、关闭或抢回系统代理。
- 真实令牌交接、配置初始化、拥有者释放，以及明确的代理启停请求继续执行原有写操作。
- 明确启用继续允许重新应用代理。`IsEnabled` 只是上次成功写入的缓存，不能因为它为真就阻止必要的手动恢复。
- Windows 代理后端使用最小内部接口，测试用记录器替换 WinINET；生产环境仍使用原有 `WindowsSystemProxy`。
- 未新增轮询、常驻进程或注册表查询，也未修改桌面层的恢复预算、避让策略、代理设置或 WSL 配置。

## 验证

先在未修复逻辑上运行回归：命名管道和本地监听两种入口各读取 100 次，均触发 100 次代理 `Enable` 调用，用例失败。修复后两种入口、开启及关闭两种偏好均为零代理写入；不会因普通授权重新取得已由其他客户端接管的代理。

Windows 专项使用当前进程的真实复制令牌验证线程模拟路径，代理本身为记录器，不修改测试电脑的代理。还覆盖明确恢复、明确关闭、写入失败保留原偏好、令牌交接与释放，并保留已取消请求的截止时间保护。
