> 2026-10-19 补测更正：本文基于 Windows 累计进程时间的 CPU 百分比保留为历史记录，不再用于证明改善或回退幅度。周期计数与 GPU 跟踪见 [CPU 计时复核](GPU-MEASUREMENT-2026-10-19.zh-CN.md)；内存、功能及调用次数分别判断。

> 2026-10-19 复核后已撤回通用分段历史缓冲和曲线快照类，日志/曲线恢复原数组实现。下文缓冲实现与第 3、4 轮矩阵保留为撤回前实验记录，不能作为当前源码收益。最终保留/撤回决定见 [多轮调优复核](PERFORMANCE-AUDIT-2026-10-19.zh-CN.md)。

本轮继续执行四项优化：连接增量更新、日志和曲线缓冲、关闭页面后的资源释放、主进程可选功能延迟加载。基线为前两轮已经完成但尚未发布的源码，包含完整文楷按需加载、故障切换投影缓存以及简中/英文收敛。现用安装未替换。

## 连接快照

原先每条连接消息都执行 `new Map(data.rows)`。现在使用按插入顺序排列的 64 项数据页：流量变化只复制受影响的数据页，索引及未变化页共享；节点新增或删除时每批只复制一次索引。空消息和实际未变化的零速率消息复用原快照。速率从非零变为零仍正常更新，累计流量按原始 bigint 精确累加。

旧快照不被后续更新修改，未变化的行对象也复用。删除和重新插入保持 Map 的顺序规则；删除积累的空位达到阈值后重建当前表，避免长期运行不断增加空洞。不会建立指向所有历史版本的引用链。

所有活动连接保留，已关闭连接仍最多保留 1,000 条，按关闭时间淘汰最旧项。连接页的筛选、排序、详情查询及最多显示 500 行的现有行为保持一致。后台仍接收连接历史，不因优化暂停无法重放的事件。

## 日志和曲线

历史缓冲保持日志 3,000 条、曲线 30 点。未被界面读取的历史按页追加，在需要数组时才生成快照。连续显示的日志使用原生数组快速路径，避免每帧逐个展开全部缓冲。暂停查看的旧日志数组以及旧曲线快照不会被新消息改写。

压力验收淘汰了始终展开环形缓冲的实现：该实现对连续显示的日志有明显 CPU 和临时分配回退。最终方案采用自适应路径，并使用共享原型访问器；没有保留每帧创建访问器和 WeakMap 记录的方案。

## 页面关闭后的资源

离开日志页时，将普通大小的日志保存为紧凑的无损表示，释放行对象和数组，重新打开时按需恢复；恢复后释放紧凑表示。不会直接删除历史，因此核心断线时仍保有先前收到的日志。ANSI、中文、Emoji、引号、换行和其他字符均按原文恢复。

为控制导航延迟，总消息文本超过 512 Ki 字符时保留原缓存，不在关闭页面时同步序列化大诊断内容。隐藏窗口和日志暂停不触发这项压缩，也不改变活动终端或编辑草稿。

配置编辑器和终端原有销毁路径经重复开关验证：CodeMirror 实例、终端实例、关闭监听器及已结束的模拟传输均释放。活动终端在隐藏和切换主题期间保持同一会话。没有销毁后台主窗口来换取低内存读数。

## 主进程延迟加载

IPC 入口仍在启动时注册。字体管理实现和报告处理实现分别在首次请求时加载，重复请求复用模块。崩溃捕获继续在原有路径立即可用；报告浏览/导出实现的延迟加载不延迟崩溃记录。

前端的数据页和历史缓冲实现也在首次实际订阅时加载，停服界面只建立轻量的空状态。页面在加载期间关闭时，取消信号会阻止后续 RPC 启动，避免产生脱离页面的订阅。生产构建首批主界面 JavaScript 为 602,820 B，低于本轮基线 603,409 B；缓冲实现作为本地延迟模块随包保留。

生产构建审计已加入两个模块，任何模块丢失或重新进入启动静态依赖图都会使检查失败。字体导入、列出、读取、选择及报告操作保留原有参数校验和错误结果。

## 压力对照

下表为独立 Node 微基准，比较同一输入、保留前后两个快照；不是整个应用的常驻内存降幅。连接样本为 10,000 条活动连接。峰值是采样到的堆增量，受垃圾回收影响，不等同于每帧分配总量或工作集。

| 场景 | 次数 | 基线时间 | 本轮时间 | 基线堆峰值增量 | 本轮堆峰值增量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 连接空消息 | 1,500 | 671.73 ms | 0.31 ms | 79.87 MiB | 0.56 MiB |
| 每帧更新 32 条连接 | 1,500 | 638.88 ms | 6.82 ms | 72.29 MiB | 7.99 MiB |
| 每帧更新全部连接 | 150 | 146.94 ms | 121.51 ms | 51.41 MiB | 30.43 MiB |
| 每帧显示日志数组 | 10,000 | 44.18 ms | 47.55 ms | 32.68 MiB | 32.01 MiB |
| 消息期间未读取日志数组 | 10,000 | 38.83 ms | 3.63 ms | 32.43 MiB | 15.16 MiB |

连续显示日志没有获得稳定 CPU 改善，保留此结果；该样本增量约为每帧 0.34 微秒。日志优化的主要收益在消息合并读取和离开页面后的存储，而不是承诺所有日志场景都更快。

另外对 3,000 条短日志做了独立保留内存测量。ASCII、中文、带转义内容的日志分别约从 497/495/389 KiB 降到 315/345/275 KiB；压缩和恢复各约 0.6–1.0 ms。数据是合成日志，不是用户日志。微基准中的显式 GC 仅用于隔离测量，没有加入应用运行逻辑。

## 四状态常驻对照

最终完整矩阵使用第 3、4 轮的 16 次独立启动、64 个样本。表中是进程树私有工作集的中位数，单位 MiB；CPU 为占一个逻辑核心的百分比，不能直接当作任务管理器整机百分比。

| 状态 | 基线内存 | 本轮内存 | 基线 CPU | 本轮 CPU |
| --- | ---: | ---: | ---: | ---: |
| 运行、前台 | 152.39 | 146.51 | 2.71% | 7.60% |
| 停服、前台 | 118.54 | 119.72 | 0.48% | 0.10% |
| 运行、后台 | 136.60 | 138.43 | 2.45% | 1.73% |
| 停服、后台 | 117.88 | 116.96 | 0.62% | 1.00% |

因此，本轮不能宣称四种状态的常驻内存或 CPU 都降低。主要确定收益是大量连接更新的临时分配下降；轻负载常驻内存的结果混合。运行前台 CPU 的高值主要来自第 3 轮 GPU 进程的 1,515.625 ms 增量，第 4 轮相应增量为 31.25 ms，需单独保留并补测，不能从汇总中删除。

完整矩阵传输 95,748,096 字节，零传输失败，每次配置替换核对均通过。窗口始终原生隐藏，前台由页面可见性模拟，使用自有回环代理、32 个合成节点、668 条规则、完整文楷和硬件加速；未包含现用安装的特权服务/应用工作进程，不能等同于现用应用的任务管理器总量。

前期第 1、2 轮用于发现停服启动开销，未混入最终矩阵。独立诊断中，两版 DOM 节点和监听器数相同，30 秒 JS 使用堆约为 4.17/4.16 MB，未观察到该样本的 JS、DOM 或字体对象增长；诊断中的显式 GC 不计入正常测量，也未加入产品。
