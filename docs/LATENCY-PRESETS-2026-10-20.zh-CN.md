# 地区响应上限的设计依据

本文保留 2026-10-20 响应阶段预设的分析。2026-10-22 已新增独立完整请求预算与有限异常窗口；只在建连阶段发生的缓慢现在也参与质量判断，见[后续修复与验证](QUALITY-FAILOVER-2026-10-22.zh-CN.md)。下文关于原先只看 HTTP 响应的描述属于当时实现。

## 目标与计时口径

目标是发现当前入口持续明显变慢，并且有合格备用时切换。上限不能照搬用户举出的 ping 数字，也不能把完整 HTTPS 请求当成一次网络往返。

检查现有实现后，各阶段含义如下：

- `tcpMs`：连接本机回环 HTTP 探针，不能代表到远端节点的 RTT。
- `connectMs`：收到本机代理 CONNECT 响应的时间。在本次样本里中位数约 1 毫秒，也不能拿来当远端 RTT。
- `tlsMs`：TLS 建连阶段，可能包含远端拨号、握手及其他处理；协议及代理链不同，不能用固定除数换算成 ping。
- `httpMs`：TLS 完成后发出 HEAD，到收到完整 HTTP 响应头的时间。包含网络往返、站点处理和响应头传输。
- `totalMs`：以上阶段的完整耗时。

采用第二快的成功 `httpMs` 作为代理响应指标；三个目标至少两个成功才可达。不能据此声称测到了 ICMP ping，但它比完整建连时间更适合本次持续响应延迟判定。单个站点变慢不会独自触发高延迟切换。

计时边界与 [Node TLS 的 secureConnect 事件定义](https://nodejs.org/api/tls.html#event-secureconnect)相符。`httpMs` 已由原探测记录，不增加新请求、ping 子进程、后台定时器或基线学习。连接和握手耗时仍在日志中供诊断；仅发生在建连阶段的缓慢不会冒充 HTTP 响应高延迟，达到总超时则仍按连接失败处理。

## 本机历史记录

本次只读分析使用 2026-10-20 **北京时间 10:51–17:57** 的现有健康日志。没有切换节点、重载代理、改变系统代理或 TUN。节点以 A、B、C 匿名，未保留地址、凭据或具体服务商名称。

美西三个有有效响应的节点共有 **588 个**可用时延样本；另有三个节点只有不可达结果，没有混入正常时延统计。少数失败和未知耗时会中断高延迟连续段，不能直接跳过。欧洲只有 3 个有效样本，HK 没有足够本机样本。

| 美西样本 | 有效轮数 | HTTP 响应中位数 | HTTP P95 | 完整 HTTPS 中位数 | 完整 HTTPS P95 |
|---|---:|---:|---:|---:|---:|
| A | 196 | 208 ms | 832 ms | 795 ms | 2794 ms |
| B | 198 | 199 ms | 331 ms | 764 ms | 1622 ms |
| C | 194 | 203 ms | 495 ms | 787 ms | 2668 ms |

P95 表示约 95% 的有效样本不超过该值。B 的响应波动较小；不能把 A、C 已有的慢响应尾部一起抬高成“正常上限”。完整耗时与响应耗时差距明显，因此原先按完整请求设置的 2500 ms 也不能用来解释 500 ms 的 ping。

## 美西候选值比较

在相同历史记录中统计“至少连续三次超标、首末探测间隔至少 10 秒”的偏慢段。失败或未知耗时重置连续段；超过两分钟的断采样不视为连续。

| 响应上限 | A 的偏慢段 | B 的偏慢段 | C 的偏慢段 |
|---|---:|---:|---:|
| 300 ms | 6 | 1 | 1 |
| 350 ms | 6 | 0 | 1 |
| 400 ms | 1 | 0 | 1 |
| 450 ms | 1 | 0 | 1 |
| 500 ms | 1 | 0 | 0 |
| 600 ms | 1 | 0 | 0 |
| 700 ms | 0 | 0 | 0 |

选择 **450 ms** 的理由：

1. 稳定参考 B 的中位数约 199 ms、P95 为 331 ms。备用需要低于上限的 80%；因此上限至少应高于 `331 / 0.8 ≈ 414 ms`，向上取 50 ms 档位得到 450 ms。此时备用的合格线为 360 ms，覆盖参考链路的多数正常波动。
2. 300–350 ms 比较敏感；400 ms 的备用合格线仅 320 ms，已低于参考 B 的 P95，余量偏小。
3. 450 ms 可以标出 A、C 的持续偏慢段；提高到 500–600 ms 后，C 的这一段不再被标出；700 ms 则两段都未标出。

这只是历史响应段比较，**不是准确的自动切换次数或误报率**：旧采样没有新规则的五秒复核频率，也缺少故障的独立人工标注；不能插值假定未采样期间一直高延迟。真正切换仍需备用连续合格、新鲜证据、切换前复核与冷却条件。所有候选都慢时不切换。

## 其他地区的初始值

公开参考使用 [Azure 地区间 RTT 数据](https://learn.microsoft.com/en-us/azure/networking/azure-network-latency)。检索时该表注明数据版本为 2026-07-30，是 Azure 骨干网络的 30 天 P50，**不是本机公网或代理实测**。以其东亚来源的时延档位作量级参考，并结合本机美西响应较骨干 RTT 更高、存在接入及站点开销这一事实留余量。

近邻地区采用 200–350 ms 的暂定响应预算，避免直接把云内低 RTT 用在公众跨境接入；南亚、美西为 450 ms；其余跨洲地区按距离、覆盖城市跨度和潜在绕路留出 500–800 ms 的预算。具体数值见[配置说明](PRIORITY-FAILOVER.zh-CN.md)。这些预算是工程初值，不是由公开 RTT 精确换算出的实测结果；尤其不能用少量欧洲样本宣称已验证全欧洲。

预设以中国大陆出发的链路为参考，其他出发地、运营商、隧道和落地链路可能需要调整。每组上限可分别覆盖或关闭，未知或混合地区不会猜测套用。小众地区可以后续补充。运行时仅使用固定阈值、有限计数和已有探测数据；本次离线分位数分析不会成为常驻机制。
