# 建连缓慢与间歇异常的故障切换修复

源码修复，尚未发布或安装。既有地区响应预设、自定义顺序、多地区按使用监测和连接失败逃离逻辑继续保留。

## 漏判与修复

2026-10-21 的只读检查发现：当前入口在成功与失败之间交替时，每次成功都会抹掉连续失败；TLS 建连约 2.7 秒时，握手后 HTTP 响应只有约 206 ms，原质量判定也不会超限。因此，“没达到原有条件”不等于业务使用正常。

现在并列使用三种证据：

1. 连续不可达达到已配置故障确认次数，按既有路径逃离故障节点，允许绕过冷却。
2. HTTP 响应或完整 HTTPS 请求连续三轮超限，首末探测开始时间至少相隔十秒。
3. 两分钟内有限窗口反复异常，默认最近五轮至少三轮失败／超限，最新一轮仍异常，首末至少相隔十秒。确认次数大于三时，窗口为 `2N−1`、至少 `N` 异常，最多 39 个标记。未知耗时、休眠／断采样、手动改选及监测暂停会清理相关证据。

后两种质量切换仍需冷却、配置顺序、新鲜备用结果和切换前独立复核；备用的 HTTP 与完整耗时都需留出 20% 余量。短窗切换还排除窗口内仍有异常的备用。排队中恢复、停止、手动选点或备用复核变慢，会撤销旧决定；不会跳到 DIRECT 或为局部地区故障强制重启全部代理。

## 两个独立的绝对预算

HTTP 响应上限 `C` 继续按地区／用户设置使用。完整请求另用 `max(1500 ms, 4C)`，包含本地连接、代理 CONNECT、远端拨号、TLS 和响应头；不从中估算 ping。两项都取原先三个目标中第二快的成功值，一个慢站点不能独自判定节点异常。

例如 HK 默认响应 200 ms、完整 1500 ms；美西响应 450 ms、完整 1800 ms；欧洲响应 600 ms、完整 2400 ms。关闭本组高延迟切换会同时关闭两项延迟预算，连续／反复不可达仍可切换。

四倍是完整多阶段请求的工程预算，不是“RTT 乘四”的测量换算。复核 2026-10-20 北京时间 10:51–17:57 的已有美西日志：相对稳定参考节点的 198 轮成功结果，完整请求第二快值中位数约 764 ms、P95 约 1415 ms，9 轮达到 1800 ms；两个其他参考的完整 P95 约 2.6 秒。1800 ms 留出了正常建连余量，又能覆盖约 2.7–3.7 秒的明显慢建连。此分析不构成故障真值、误切率或公网性能保证；其他地区仍为工程初值。

## 资源与持久化

没有基线学习、吞吐测试、新目标或常驻计时器。正常间隔不变；异常之后用既有调度器进行有限五秒复核，连续断线仍用原先一秒确认。确认异常但没有合格备用后回到异常间隔。所有地区继续共享最多三个节点探测槽位、最多两个备用。

只增加每节点有限的异常标记和开始时间，不保存延迟样本数组。日志增加完整耗时字段以及 `unstable` 切换原因。没有新增设置字段或迁移兼容层；另修正手动首选变化事件写运行快照时携带旧 selected 的次序问题。

## 验证与边界

- 主进程隔离回归：132 项通过，包含真实回环 TLS 延迟、慢握手但快响应、地区预算差异、反复失败／混合异常、孤立波动、无备用时退避、过期证据、冷却、备用复核变慢取消及手动首选快照。
- Dashboard：20 个文件、152 项通过；修改文件的 ESLint、主项目 TypeScript 和 Electron Vite 构建通过。
- 隐藏 Electron 实际设置组件验证通过，未使用用户鼠标或连接现用守护进程。

真实 TLS 测试在 CONNECT 后暂缓转发 ClientHello，证明完整耗时确实涵盖建连等待；它仍是隔离回环，不能证明生产网络或带宽改善。旧日志未保存完整的探测开始与调度状态，且新策略会改变后续采样频率，因此不能宣称旧事件在新策略下一定会于某秒切换。

应用本轮源码前的运行实例仍使用旧策略；本轮未自动安装、重载用户服务或更改节点。Hugging Face 规则分类由 Deploy 公共模板与权威配置另行修复，不通过 Route 主进程硬编码用户域名。
